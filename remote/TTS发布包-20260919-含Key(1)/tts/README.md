# TTS 模块（分工 2）

文本进，声音出。云端合成、可被按键打断、演示前可预热缓存提速（**可选**，见 6.5 节口径说明）。

```
speak(text) -> 声音
```

## 2. 安装

**开发机（Windows）**

> Windows 上**什么都不用装**：模块会自动用标准库 `winsound` 出声。
> 只有想换更好的后端（更低延迟、更细粒度的打断）才需要装 `sounddevice`。

```bash
set MIMO_API_KEY=xxx
python test_tts.py
```

**开发机（macOS / Linux）**

```bash
pip install sounddevice        # pip 轮子自带 portaudio，最省事
export MIMO_API_KEY=xxx
python test_tts.py
```

**树莓派（Pi OS Lite 64-bit）**

> 核心链路在 Linux 上反而更简单：`aplay` 是系统自带的，**不装任何 pip 包就能出声**。
> 代码里 winsound 分支有平台判断，在 Linux 上会自动跳过，探测顺序落到 aplay。

```bash
sudo apt update
sudo apt install -y alsa-utils       # 提供 aplay —— 这是唯一的系统依赖
sudo usermod -aG audio pi            # 音频设备权限，重新登录后生效
```

> ★ **不要在 Pi 上执行 `pip install -r requirements.txt`。**
> 本模块零第三方依赖；`requirements.txt` 里那些包都是可选的、装了也不会被用上，
> 其中 `PyAudio` 还要现场编译 PortAudio，纯浪费时间。
>
> **完整的部署步骤**（SD 卡烧完之后要做什么、`.env` 怎么填、怎么验证真的出声、
> Windows→Pi 的三个传文件坑）见项目根 **`烧入树莓派清单.md`**；
> 双击 **`导出给树莓派.bat`** 可以生成一个干净、只含必需文件的待拷目录。

**关于本地离线引擎（Piper）—— 已评估，已放弃**

> **结论：不做。** 2026-09-17 实测听感后由模块负责人决定裁掉，相关代码、脚本与
> 60 MB 模型已从仓库移除。
>
> **理由（按重要性）**：
> 1. **音质不达标**——Piper `zh_CN-huayan-medium` 与云端神经网络 TTS 的听感差距明显。
>    导游产品的核心价值是"讲清楚"，音质不合格等于功能不合格。
> 2. **项目确定为有网络环境运行**（4G / 移动 WiFi），离线不再是必须项。
> 3. 保底需求改由成本更低的**预热音频缓存**承担（见 6.5 节），且播的是**云端音质**。
>
> **留档（曾被验证过，不再维护）**：piper-tts 1.8.0 在 x86 上约 45x 实时；
> 252 字纯离线零失败；模型 60 MB；**必须 aarch64 系统**（PyPI 上无 armv7l 轮子）。
> 若将来真要做无信号景区，重做时注意：**piper-tts 1.3.0+ 已删除
> `synthesize_stream_raw`**，须改用 `voice.synthesize()` 迭代 `AudioChunk` 取
> `chunk.audio_int16_bytes`；只按旧 API 写会 `AttributeError` 并静默失效。

## 3. 接口

```python
import tts

tts.speak("欢迎来到外滩。")         # 阻塞到播完，返回 True/False
tts.speak(text, wait=False)        # 后台播报，立即返回
tts.feed("第一句。")               # 追加，不打断正在播的声音（流式 LLM 用）
tts.stop()                         # 立刻静音
tts.is_speaking()                  # -> bool
tts.set_volume(80)                 # 0-100
tts.set_voice("白桦")               # 切换音色
tts.warmup()                       # 开机预热（建议接进 systemd）
```

**`feed()` 是什么**

给流式 LLM 用的接口。Agent 用流式模型生成讲解文案时，可以「生成完一句就喂一句」：

```python
for sentence in llm_stream:     # 伪代码
    tts.feed(sentence)
```

这样**第一句生成完就开始播**，用户不用等整段 LLM 生成完。

> 能快多少取决于 LLM 的生成速度：`test_stream_llm.py` 在「每句 1.0 s」**假设**下
> 模拟出 2.9 s，**属模拟值而非实测**，引用前先看 Agent 给的真实生成耗时。

- 正在播报时调用 → 追加到队尾，不打断
- 空闲时调用 → 等价于 `speak(text, wait=False)`，自动启动
- 连续 1.5s 没有新 feed → 自动收尾（`TTS_FEED_IDLE` 可调）

**对非流式 LLM 完全无影响**：它照常一次性调 `speak()` 即可，`feed()` 只是多了一个可选入口。
**本项目 Agent 已确认为非流式 LLM，走的就是这条路径** —— 即模块当前的主路径，
所有实测数据（首字 0.84 s 中位等）都是在"整段文本一次性到达"的前提下测出来的。
`feed()` 保留可用（已回归验证），将来换流式模型可直接接上，零成本。

**返回值语义（已和契约一致，别改）**

- `True` = 完整播完
- `False` = 被 `stop()` 打断，或全部句子合成失败

`speak()` **任何情况下都不抛异常**。TTS 挂了最多是没声音，不能把整个导游装置带崩。

**预置音色**：`REDACTED-ROTATE-ME`、`冰糖`、`茉莉`、`苏打`、`白桦`、`Mia`、`Chloe`、`Milo`、`Dean`

### 3.1 契约接口（给 Agent 核心用的）

《熊导游项目 模块接口契约 v1.0》规定 TTS 模块要提供 `tts/tts_interface.py`。
已实现，用法：

```python
from tts.tts_interface import TTSInterface, TTSAdapter, get_tts

adapter = get_tts()                                   # 进程内单例
st = await adapter.speak("欢迎来到外滩。", interrupt=False)
if not st.success:
    print(st.error_msg)                               # 失败原因，不抛异常
```

**这是适配层，不是第二个引擎。** 里面还是上面那个 `tts.py`，只是包成契约要求的异步形态：
引擎是"同步 + 后台线程"的，适配层用 `asyncio.to_thread` 把它挪到工作线程，
事件循环不会被卡住（重写成 asyncio 原生反而会丢掉已实测的时序特性，收益为零）。

语义如下 —— **其中 4 处需要 Agent 确认**，清单见项目根《接口契约待确认问题-回Agent.md》：

| 项 | 当前实现 |
|---|---|
| 阻塞性 | `await` 到**播完**才返回；此时 `is_playing` 通常为 `False` |
| `interrupt=True` | 立刻打断当前播报，改播新文本 |
| `interrupt=False` | 正在播报时**等它播完**再播（排队，不丢内容） |
| 超时取消 | 外层 `wait_for` 超时时：**先停音频**，再把 `CancelledError` 原样抛出 |
| 业务异常 | 一律封装进 `error_msg`，**不外抛** |
| 并发 | 同一进程只有一路音频；后启动的抢占先启动的，被抢占方返回 `success=False` |

关于最后那条"超时取消"：契约第 4 条要求"内部异常不许抛出"，我们把 `CancelledError`
当成例外处理 —— 它属于**调用方的控制流**（`wait_for` 超时、任务被 cancel），
吞掉它会让外层的超时机制彻底失效。但"超时后声音必须真的停"这条已经做到并测过，
不会出现"Agent 已经放弃，熊还在说话"。

`speak()` 的 timeout 由接约方自己用 `wait_for` 控制（契约里本模块没有 timeout 参数）。

自测：`python test_interface.py`（离线，mock 合成 + 干跑播放，走真实时序、不发网络）
或 `python test_interface.py --online`（真实云端）。8 个情景 / 29 项断言。

## 4.6 场景转换（讲解目标切换）的情景测试

现场除了"讲什么"，还有"换目标讲"：游客走到下一个点位，讲解目标就变了，
上一段必须**立刻掐断**、新一段马上接上。专项脚本 `test_scene_switch.py`
用外滩 8 个讲解目标跑 6 个情景：

```bash
python test_scene_switch.py            # 默认 dryrun：不出声，但按真实时长走
python test_scene_switch.py --speak    # 真的出声
python test_scene_switch.py --only 2,3 # 只跑指定情景
python test_scene_switch.py --list     # 列出情景
```

| 情景 | 内容 | 结果 |
|---|---|---|
| 1 | 自然更替（讲完再接） | 全部讲完，零降级 |
| 2 | **中途打断**（讲到一半目标突变） | `stop()` 0 ms，切换成功 |
| 3 | 连续抖动（3 秒内连切 3 次） | 无串台、无堆积 |
| 4 | 切回讲过的目标 | 命中缓存，0.01 s |
| 5 | 被打断的半句会不会写坏缓存 | 缺陷已修（见下） |
| 6 | 切换时云端挂掉 | 0.33 s 放弃，不卡流程 |

**切换延迟（目标变更 → 新目标第一个字出声）**：

| 类别 | 实测 | 说明 |
|---|---|---|
| 冷（首次到该点位） | **0.66 – 1.29 s**（中位 ≈0.8s） | 全是网络首字，**现场真实手感** |
| 热（走回头路 / 预热命中） | **0.01 – 0.44 s**（中位 ≈0.2s） | 网络成本为 0 |

> 热切换偶尔不是"瞬时"：相隔 1 秒级的**快速连切**时，`speak()` 要同步等上一条
> 流水线收尾，实测该等待可达 0.43 s。正常游览节奏（点位间隔数秒以上）碰不到。

> **该测试发现并修复了一个真 bug**：原先"被打断的句子"会把**只收到一半的音频**
> 写进缓存（实测一句完整 2.08 s 被存成 0.80 s）。缓存无法自证残缺，一旦写入
> 就永久错误——命中缓存播放时会播出被砍半截的讲解。修复后**只有整句收完才写缓存**，
> 情景 5 现为常驻回归项。

## 6. 它到底怎么工作的

```
text → 分句器 → 合成线程 → 云端 MiMo-V2.5-TTS（pcm16, 24kHz）
                                    → 预取队列(2) → 播放线程 → 扬声器
                                                        ↑
                                                  stop_event 清队列 + abort
```

- **真流式逐块推送**：合成端边收 SSE 边把 PCM 块推进队列，播放端立刻开播。
  首块到达即开声（实测 0.7–1.0 s），**不等整句生成完**。
- **分句的目的不是降延迟**（首块延迟与长度无关），而是：降级粒度、缓存粒度、语境自然度。
  所以长度放宽到 **80 字软切 / 120 字硬切**，切太碎反而让句间停顿生硬。
- **逐句容错**：某句云端失败就跳过该句；连续失败 2 次则本次播报**剩余句子直接跳过**，
  不再逐个等满超时——避免游客对着机器干等半分钟。实测凭据无效时 6 句只尝试 2 次、
  总耗时 0.66 s 就返回。
- **打断三步**：置位 `stop_event` → 清空预取队列 → `abort()` 播放流。
  只做第三步会出现"静音 0.3 秒后又冒出半句话"。
- **播放层按采样率重开流**：不同采样率的音频块不会混进同一个播放流。
- **四种播放后端自动探测**（按优先级）：
  | 后端 | 平台 | 说明 |
  |---|---|---|
  | `pyaudio` | 全平台 | 需 `apt install portaudio19-dev` |
  | `sounddevice` | 全平台 | pip 轮子自带 portaudio，开发机推荐 |
  | `winsound` | 仅 Windows | **零依赖**，标准库；但只能一次播一个文件，所以**整句缓冲**后才播，首字延迟多 1-2 秒。想真流式就装 `sounddevice` |
  | `aplay` | Linux | 子进程管道，**Pi 上的默认**（零安装、真流式）|
  | `dryrun` | 全平台 | 不发声，只跑逻辑 |
- **音频缓存**：`sha1(音色+文本)` 命中则零延迟复用。评委连按同一景点时效果显著。

## 6.5 演示提速（可选）：预热音频缓存

设备在有网络环境下运行，但**现场网络可能抖动**。本模块的音频缓存是落盘的，
且命中判断发生在发起网络请求**之前** —— 所以提前预热即可完全脱离网络播放。

```bash
# 演示前（联网时）：把路线上的讲解词全部预合成落盘
python precache_cli.py demo_script.txt

# 现场演示前：复核缓存是否齐备（只校验，不合成）
python precache_cli.py demo_script.txt --check-only
```

`demo_script.txt` 每行一条讲解词，`#` 开头为注释。

**实测（2026-09-17，真实云端接口）**：预热 3 条讲解词（切分 5 句）耗时 8.4 s，缓存体积 1.2 MB。
随后清空 API Key，模拟"现场断网"：

| 场景 | 结果 |
|---|---|
| 断网 + 缓存开启 | **3/3 成功**，拿到音频耗时 5–10 ms |
| 断网 + 缓存关闭（对照组） | 3/3 失败 |

对照组成立，证明出声确实来自缓存。

**三个前提**（否则预热白做）：

1. **讲解词要提前拿到** —— 缓存键含文本，措辞一变即失效
   （09-19 修订：**不再要求上游改机制**，拿不到就不预热）
2. **现场的 `TTS_VOICE` / `TTS_FORCE_ENGINE` 必须与预热时一致** —— 缓存键 = `sha1(force_engine|voice|文本)`
3. **预热须在云端可用时做** —— 没有网络就合成不出音频，脚本会直接报错中止

> **09-19 17:20 口径修订**：本节原称"唯一的断网保底手段"，**已改**。
> 断网时 TTS 是**最后**受冲击的模块（链路 `识图/定位 → LLM 生成文案 → TTS 合成`）——
> 前面任一环断了，本模块根本没文本可播，缓存里存着音频也不知道该播哪条。
> 要三个模块**同时**做文本固化才成立的"整机断网保底"，**协同成本远超收益，已明确不做**。
>
> 现在它的定位是**体验优化**：首字 0.8 s → ≈0、同景点重按秒出、
> **抗 TTS 厂商 API 抖动/限流**。**不做也能正常演示**，代价仅首字 0.8 s。
> 成本对比：不用 60 MB 模型、不用部署推理环境、不用改 systemd，演示前跑一次脚本即可，
> 而且保下来的是**云端音质**。

## 7. 降级矩阵

> ⚠️ **本模块已无本地离线引擎**。云端不可用时，唯一能出声的途径是
> **命中预热缓存**（6.5 节）——**但这不构成"断网保底"承诺**：
> 断网时上游没有文本，本模块也无从播报。这一点必须在整机方案里说清楚。

| 触发 | 行为 |
|---|---|
| 单句超时 / 连接错误 / 返回空 | 跳过该句，继续下一句（已播部分不回退） |
| 连续 2 次云端失败 | 本次播报**剩余句子全部跳过**，不再逐个等超时 |
| 全部句子失败 | `speak()` 返回 `False`，**绝不抛异常**（硬约束：TTS 故障最多没声音，不能让整机崩） |
| 缓存命中 | 在发起网络请求**之前**返回，彻底不依赖网络 |
| 采样率不一致 | 播放层重开流，不混采样率 |
| 音量控制 | 优先 `amixer`（Pi），失败退化为软件增益（0-100 → 0-1.5x） |

### 英文支持

能说。实测 198 字符英文讲解词：3 句、首字延迟 0.96s、全程云端无失败。

三个已经处理好的点：

1. **英文句号分句**：`.` + 空格/行尾才算句末（所以 `3.14` 不会被切开）
2. **缩写保护**：`Dr.` / `U.S.` / `e.g.` / `Mr.` 等不会在中间断句（内置一张缩写表）
3. **风格自动切换**：检测到拉丁字母过半就换英文风格描述，不用手动改

```bash
python test_tts.py --text "Welcome to Shanghai University. This is the Cherry Blossom Avenue."
```


## 7.5 树莓派部署要点

> **完整部署步骤见项目根的 `烧入树莓派清单.md`** —— 含"SD 卡烧完之后要做什么、
> `.env` 三个值怎么填、怎么验证真的出声、Windows→Pi 的三个传文件坑"。
> 本节只列技术要点。

### 播放后端（Linux）

| 后端 | 是否流式 | 说明 |
|---|---|---|
| `aplay` | ✅ 真流式 | **零安装**，alsa-utils 自带；走管道写 stdin |
| `pyaudio` | ✅ 真流式 | 需 `apt install portaudio19-dev` |
| `sounddevice` | ✅ 真流式 | 需 libportaudio2 |
| `winsound` | — | Linux 上不存在，自动跳过 |

探测顺序：pyaudio → sounddevice → winsound → aplay。
**什么都不装就会落到 aplay，这是最省事的路径。**

### 确认音频设备

```bash
aplay -l
```

典型输出：

```
card 0: Headphones [bcm2835 Headphones], device 0     ← 板载 3.5mm（PWM，底噪大）
card 1: Device [USB Audio Device], device 0           ← USB 音箱
```

然后：

```bash
export TTS_ALSA_DEVICE=plughw:1,0
python test_tts.py
```

> ⚠️ 用 **`plughw:`** 而不是 `hw:`。
> `hw:` 是直连硬件，不支持任意采样率，云端 24000Hz 会直接报错；
> `plughw:` 会自动重采样（`hw:` 只接受设备原生采样率，24000Hz 会直接失败）。

### 权限

```bash
sudo usermod -aG audio pi      # 把运行用户加进 audio 组
# 重新登录后生效
```

### systemd（交给整合者）

见同目录 `tts.service` 示例。三个要点：

1. `Environment=` 里放 `MIMO_API_KEY`、`TTS_ALSA_DEVICE`、
   **`TTS_CACHE_DIR` 必须写绝对路径**（systemd 的工作目录不是你的 home）
2. `User=pi` + `Group=audio`
3. 开机跑一次 `warmup()`：见 service 里的 `ExecStartPre`

### Linux 上的已知差异

| 项 | Windows | Linux / Pi |
|---|---|---|
| 默认播放后端 | `winsound`（整句缓冲，+0.3s 延迟） | `aplay`（真流式，无额外延迟） |
| 音量控制 | 软件增益 | `amixer` 系统级（优先） |
| 首字延迟 | 1.38s | 约 1.07s（少了缓冲开销） |

**Linux 上的表现比 Windows 更好。**

### Windows 开发机上声音"一卡一卡的"？

那是 `winsound` 后端的固有问题：它只能一次播一个 **WAV 文件**，没法往正在播的流里追加数据。
如果每收到一个 320ms 的音频块就单独播一次，块与块之间就会有缝隙，而且异步播放时
复用同一个临时文件名还会让下一个块覆盖正在播的文件。

**已修**：winsound 后端现在会**攒够一整句再播**（用队列里的 EOS 标记判断句末），
临时文件每次独立命名并自动清理。代价是 Windows 上首字延迟多 1-2 秒
（实测 1.38s vs 真流式的 1.07s）。

**想要零延迟就装 sounddevice**，装完会自动切过去，真流式边收边播：

```bash
pip install -i https://pypi.tuna.tsinghua.edu.cn/simple sounddevice
```

> 树莓派不受影响 —— 那边走 `aplay` / `pyaudio`，本来就是真流式。
