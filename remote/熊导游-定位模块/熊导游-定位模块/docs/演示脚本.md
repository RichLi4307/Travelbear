# 演示脚本：现在有什么、怎么演、怎么讲

> 采购还没到货。这份文档解决一件事：**在没有硬件的情况下，把"链路是通的"讲清楚。**
>
> 核心原则：**不要假装有硬件。** 教授和评委见过太多"PPT 演示"。
> 你越早说清楚"哪些是真的、哪些是占位"，可信度越高。

---

## 一、演示前 30 秒准备

```bash
# 仓库根目录
pip install -r requirements.txt
python -m pytest -q                    # 先确认 110 passed，别在台上翻车

python demo/offline_demo.py            # 三幕一次演完，0.1 秒出结果
```

**这个演示没有任何停顿** —— 跑完立刻全部输出。所以当众演示时不要一次跑完，
而要**一幕一幕跑**，跑完一幕你讲一段，再跑下一幕：

```bash
python demo/offline_demo.py --acts 1                      # 演第一幕，然后你讲
python demo/offline_demo.py --acts 2 --place 外滩          # 演第二幕，然后你讲
python demo/offline_demo.py --acts 3                      # 演第三幕
```

节奏完全由你控制，不靠程序 sleep。**建议把这三条命令提前打在记事本里，现场复制粘贴。**

**建议把终端字体放大到 16 号以上**，中文对齐才看得清。

## 二、三段式演示

### 开场（20 秒）—— 一句话说清楚现在到哪了

> "硬件还在路上。今天我要证明的不是'它能用'，而是**'软件链路已经通了，
> 只差硬件输入'**。我分三步给你看。"

跑 `python demo/offline_demo.py`，它会自己打印状态表：

```
硬件状态：GNSS 模块 ✘   蓝牙信标 ✘   摄像头 ✘   扬声器 ✘
软件状态：定位 ✅   识图（假）   语音（假）   Agent（模板）
```

**这张表是你可信度的来源**——主动承认哪些是假的，后面说真的才有人信。

---

### 第 1 幕　真实调用：没有硬件时会怎样（40 秒）

**这是全场唯一一次真正的"实时调用"**，不是回放。指着屏幕说：

> "注意，这一段不是模拟。我现在真的调用 `get_location()`。"

```
t= 0.00s   按下按钮 → agent 调 location.get_location()
  { "mode": "none", "poi_name": "定位不可用", ... }
t= 0.00s   返回耗时 4.8 ms
```

要讲的三句话：

1. **"没崩、没卡住、没抛异常。"** —— 返回 `mode="none"` 是契约里的硬要求。
2. **"评委最容易记住的是'翻车了会不会崩'，不是'顺利时有多顺'。**
   演示现场断网、丢星、信标没电，这行代码保证它还能体面地说话。"
3. **"所以缺的不是软件，是硬件输入。"** ← 这句把整个演示的基调定死

---

### 第 2 幕　注入假 GPS：完整链路（90 秒）

> "现在假装我站在外滩，按了一下按钮。"

```
t= 0.00s   【用户】按下肩带上的按钮
t= 0.02s   【定位】get_location() → 「外滩」  (mode=gps, confidence=0.85)
t= 3.00s   【识图】describe_scene() → 「黄浦江边的万国建筑群…」
t= 3.10s   【Agent】生成讲解：您现在站在外滩……
t= 5.00s   【语音】speak() → 扬声器出声，约 12.5 秒
```

要讲的三句话：

1. **"定位只花了 0.02 秒。"** 因为它从开机起就在后台盯着卫星，
   **不是在按键那一刻才开始找** —— 否则要等 30 秒的冷启动。
2. **"每个模块只暴露一个函数。"** 定位 `get_location()`、识图 `describe_scene()`、
   语音 `speak(text)`。agent 负责编排，四个模块互不阻塞，四个人可以并行开发。
3. **"识图和语音这两段现在是占位数据。"** 那两个模块做出来之后，
   把 `_fake_vision` / `_fake_tts` 换成真实调用，**接口不用改**。

> ⚠️ **千万别把这两段假数据含糊过去。** 主动说"这是假的，接口已经定好了"，
> 比被人问出来强一百倍。

---

### 第 3 幕　走进室内：自动降级到蓝牙（60 秒）

```
t= 0.00s   在室外        → mode=gps  「外滩」
t=35.00s   走进展厅 35s 后 → mode=ble  「三号展厅-青铜器展位」
t=45.00s   走到门口，GPS 又有了 → mode=ble  （迟滞期内不切回去）
t=56.00s   再过 11 秒      → mode=gps  「外滩」
```

要讲的三句话：

1. **"GPS 信号穿不过屋顶。** 走进展厅 35 秒后旧定位自然过期，
   它**自己**转去扫蓝牙信标，没有任何人工干预。"
2. **"注意 t=45s 那一行没有立刻切回 GPS。"** 这是故意加的 20 秒迟滞 ——
   否则在门口来回走，模式会疯狂抖动，Agent 就会说出前后矛盾的讲解。
3. **"t=56s 才切回去。** 这些数字都在 `contract.py` 顶部，现场觉得太灵敏就改这里。"

---

### 收尾（20 秒）—— 把话头引到"下一步"

> "三种模式全部走通，110 个自动化测试全绿。
> 真正的下一步不是继续写代码，是**把采购单下掉**——
> GPS 到货那天，第一幕那个 `mode: none` 就会变成 `gps`。
>
> 这是**同一个演示**，只差硬件输入。"

## 三、按观众选版本

| 观众 | 时长 | 演什么 | 重点 |
|---|---|---|---|
| **队友**（语音/识图/Agent） | 3 分钟 | 第 1 + 2 幕 | 接口契约、怎么跑起来、`tests/` 怎么加自己的测试 |
| **教授 / 评委** | 5 分钟 | 全部三幕 | 风险可控、工程真实（有测试、有文档、有已知限制） |
| **自己练手** | 10 分钟 | 全部 + 自己改配置重跑 | 摸熟 `scenic_areas.yaml` 怎么改、判定怎么变 |

### 给队友还要多演一段

```bash
python -m pytest -q                                          # 110 passed，无需硬件
python location/tools/simulate_route.py                      # 看判定行为
```

> "你的模块照这个模式来：**一个函数 + 一个能独立跑的测试文件**，
> 文件名带模块前缀（`test_vision_*.py`），别和我这个撞名。"

## 四、还不能演示的（怎么讲）

| 不能演 | 怎么解释 |
|---|---|
| 真人按按钮、熊开口 | "硬件在物流路上。软件链路已经通了，接口是咬合的。" |
| 真实 GPS 定位 | 第 1 幕已经展示了无硬件时的行为；到货后**同一个演示**会变成 `gps` |
| 真实识图 / 语音 | 那两个模块还没人写。**接口契约已经冻结在根 README 里** |
| 整机外观 | 外壳方案定了（3D 打印硬壳熊 + 铝散热背板），还没打印 |

**主动讲"现在不能演什么"，比被人问出来强。** 而且这段话本身就在展示你的工程素养。

## 五、录屏建议（demo 视频是交付物之一）

1. **分辨率 1920×1080，终端字体 16 号以上**，中文对齐才看得清
2. **分段录，不要一镜到底。** 演示本身 0.1 秒就跑完，所以：
   - 先跑 `python demo/offline_demo.py > demo.txt`，把输出存成文件
   - 录屏时打开 `demo.txt` **慢慢往下滚**，边滚边念旁白 —— 节奏完全可控
   - 这样比录实时运行好得多：不会手抖、不会来不及讲
3. **一定要念旁白**，不要只放屏幕
4. 分三段录，最后剪在一起：
   - 第 1 段：`pytest -q` → 110 passed（2 秒，展示工程底子）
   - 第 2 段：`demo.txt` 滚屏 + 旁白（2 分钟）
   - 第 3 段：硬件到货后补录的真机段落
5. **第 3 段留到 GPS 到货再录** —— 到时候把第 2 段替换掉，视频就完整了

这份录屏现在就能交，硬件到货后只需**补录替换其中一段**。

## 七、这个演示的价值在哪

它证明的不是"我能写出能跑的代码"，而是：

1. **接口先冻结、再并行开发** —— 四个人不互相阻塞
2. **每个模块能独立自测** —— 110 个测试不需要任何硬件
3. **失败路径被认真对待** —— `none` 不是意外，是设计
4. **知道自己的边界** —— 哪些是真的、哪些是占位、下一步缺什么

这四条，比一个炫酷但跑不起来的 demo 值钱得多。
